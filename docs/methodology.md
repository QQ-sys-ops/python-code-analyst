# 项目理解方法论

> **版本**: v2.0  
> **来源**: project-understander 技能  
> **适用场景**: 新人接手项目、项目交接、快速理解项目整体结构  
> **独立版本**: 不依赖任何特定 AI Agent 平台

---

## 定位

- 回答"这个项目怎么理解？怎么接手？"
- 不是代码质量分析，而是项目认知建立
- 不是函数级细节，而是项目级全景

**与代码分析工具的关系**：
- 本方法论：项目理解（架构→数据流→模块职责）
- 代码分析工具：代码分析（复杂度→调用图→问题发现→报告）

## 十步方法论

### Step 1: 扫描项目结构

提取：文件数量、行数、目录结构、配置文件、数据文件。

```bash
find <project> -name '*.py' -o -name '*.json' -o -name '*.yaml' | head -50
wc -l <project>/src/*.py
```

### Step 2: 构建数据流图（核心步骤）

**方法论：数据流驱动，而非代码结构驱动**

1. 找到原始数据入口（CSV/JSON/数据库/API）
2. 追踪数据经过的每个处理环节
3. 识别输出产物（模型/报告/文件）
4. 画出完整数据链路

**关键原则**：数据流 ≠ 代码调用链。数据流描述"数据怎么流动"，代码调用链描述"函数怎么调用"。项目理解应优先追踪数据流。

### Step 3: 确定架构分层

**防错规则：同一模块只能出现在一个层级**

| 层级 | 包含什么 | 不包含什么 |
|------|---------|-----------|
| 应用入口层 | train.py, predict.py, evaluate.py | process.py（它是数据预处理） |
| 数据预处理层 | process.py, data_pipeline.py | dataset.py（它是运行时加载） |
| 数据能力层 | tokenizer.py, dataset.py | model.py |
| 模型层 | model.py, network.py | config.py |
| 配置层 | config.py, settings.py | — |

**常见错误**：把process.py同时放在"应用入口层"和"数据层" → 职责边界模糊。

### Step 4: 确定推荐阅读顺序

**方法论：按数据流顺序阅读，而非按字母/文件大小**

正确顺序 = 配置 → 数据入口 → 数据处理 → 数据加载 → 模型 → 训练 → 推理 → 评估

```
config.py → tokenizer.py → process.py → dataset.py → model.py → train.py → predict.py → evaluate.py
```

**错误顺序示例**：
```
config.py → tokenizer.py → model.py → dataset.py → process.py  ❌
```
原因：把model.py放在dataset.py和process.py之前，会让读者过早进入模型结构，没先理解数据如何进入模型。

### Step 5: 分析模块职责与依赖

用grep提取import关系，构建模块依赖图。标注：
- 哪些模块是"叶子节点"（不被其他模块依赖）
- 哪些模块是"枢纽节点"（被多个模块依赖）
- 是否存在循环依赖

### Step 6: 风险识别与分级

**框架：正确性 > 稳定性 > 可维护性 > 可读性**

| 优先级 | 类别 | 典型问题 | 示例 |
|--------|------|---------|------|
| **P0** | 正确性bug | 数据处理错误、编码错误、逻辑错误 | padding_value=0硬编码、eos缺失导致ValueError |
| **P0** | 稳定性风险 | 训练崩溃、评估中断、内存溢出 | 无梯度裁剪、PositionEncoding max_len硬编码 |
| **P0** | 泛化风险 | 无验证集、过拟合检测缺失 | best_model仅根据train loss保存 |
| **P1** | 可复现性 | 缺requirements.txt、环境不明确 | 无版本锁定 |
| **P1** | 可维护性 | 缺docstring、配置硬编码 | 超参写死在代码里 |
| **P1** | 功能缺失 | 缺少常见功能 | 无checkpoint续训、无学习率调度 |
| **P2** | 优化 | 性能、精度提升 | BPE/subword、Beam Search |
| **P2** | 部署 | 导出、量化、服务化 | ONNX导出、模型量化 |

**关键原则**：requirements.txt和docstring虽然重要，但它们影响的是可复现性和可维护性，不是正确性。P0应优先修复直接影响程序正确性和运行稳定性的问题。

### Step 7: 交叉验证

**方法论：用外部资料验证内部判断**

| 验证源 | 用途 | 方法 |
|--------|------|------|
| GitHub同类项目 | 架构合理性 | 对比相似项目的目录结构和模块划分 |
| 官方文档 | API使用正确性 | 验证框架API调用是否符合文档 |
| CSDN/博客 | 最佳实践 | 对比训练策略、数据处理流程 |
| PyTorch/HuggingFace教程 | 标准流程 | 验证数据流是否符合标准pipeline |

**验证输出**：标注每个关键判断的验证状态
- ✅ verified — 与外部资料一致
- ⚠️ partial — 部分一致，有差异
- ❌ refuted — 与外部资料矛盾
- 🔍 unverified — 未验证

### Step 8: 生成10节标准报告

按标准报告模板组织（见 report-template.md）。

### Step 9: 统计口径声明

**必须在报告中声明**：

```
统计口径说明：
- 行数统计：以源码快照为准，含空行和注释，不含__pycache__
- 函数数量：包含类方法和模块级函数，含__init__
- 文档覆盖率：有docstring的函数数 / 总函数数（含类方法）
- 复杂度：圈复杂度(CC)，基础分1，每个if/for/while/except/with加1
```

### Step 10: 表述严谨性检查

**禁止使用的绝对表述**：

| 不准确 ❌ | 准确 ✅ |
|-----------|---------|
| "逐字分词无法处理未登录词" | "逐字分词语义粒度较粗糙，无法显式表示词级或子词级结构" |
| "32MB模型无法部署" | "当前项目未提供部署链路，可考虑ONNX导出和量化" |
| "这是死代码" | "这是独立验证/演示脚本，不属于主流程" |
| "必须重构" | "建议重构，当前实现存在X问题" |
| "完全不可用" | "在X场景下可用，Y场景下受限" |

**原则**：描述事实和限制，而非下绝对判断。用"可考虑"、"建议"、"当前未提供"替代"无法"、"必须"、"完全"。

## 实战陷阱

### 1. 阅读顺序陷阱
**问题**：按代码结构（config→tokenizer→model→dataset→process）排序，把model.py提前
**正确做法**：按数据流排序（config→tokenizer→process→dataset→model），先理解数据再理解模型

### 2. 架构分层重复陷阱
**问题**：process.py同时出现在"应用入口层"和"数据层"
**正确做法**：process.py是数据预处理入口，归入数据层；应用入口层只放train/predict/evaluate

### 3. 风险优先级失真陷阱
**问题**：把docstring缺失和requirements.txt列为P0，而padding_value硬编码、无验证集列为P1
**正确做法**：P0=正确性bug+稳定性风险+泛化风险；P1=可复现性+可维护性+功能缺失

### 4. 表述绝对化陷阱
**问题**：写"32MB模型无法部署"、"逐字分词无法处理未登录词"、"这是死代码"
**正确做法**：描述事实和限制，用"可考虑"、"建议"、"当前未提供"替代绝对判断

### 5. 统计口径不清陷阱
**问题**：报告写"582行/28函数/21%覆盖率"但没说明统计方法
**正确做法**：声明统计口径（含/不含什么），标注可能的差异来源

### 6. Mermaid图表兼容性
**问题**：Mermaid语法在部分渲染器中显示异常
**安全写法**：用 `graph` + 无引号 + 无特殊字符 + 无subgraph

### 7. 大型项目性能
**问题**：文件太多分析慢
**缓解**：优先分析src/目录，跳过.venv/node_modules/__pycache__
